# Feature Specification: The corpus and the canary

**Feature Branch**: `007-corpus-and-canary`

**Created**: 2026-09-06

**Status**: Draft

**Input**: User description: "https://github.com/galax-io/parsec/milestone/12"

**Milestone**: v0.0.7 — The corpus and the canary (parsec#14, #60, #61)

---

## Context

Five real recordings exist under `testdata/corpus/gatling/`, one per supported version, each
committed with the account Gatling gave of that run. A canary workflow runs a live Gatling against
the probe simulation and holds the decoder to the report that run generated for itself.

Three gaps remain, and together they are what stands between the codecs and the v0.0.7 → v0.1.0
freeze that parsec#13 asks for:

1. **The canary runs text versions only** (3.11.5, 3.12.0). Nothing exercises the binary codec —
   the newer, riskier half, and the one that shipped a panic in v0.0.5 — against a Gatling that ran
   a minute ago.
2. **Verification stops at the run total.** For a binary recording only the global
   total/OK/KO triple is held to the run's own report; the per-request rows that report carries are
   never read. A decoder that renamed every request but kept the totals passes today.
3. **The corpus cannot be regenerated by one command.** Recording a version is a documented
   nine-step manual procedure needing a local JDK, sbt and a stub, so it will not be repeated when a
   new Gatling appears.

Two further gaps make the evidence weaker than it reads:

4. **No workflow ever passes `-fuzz`.** Three fuzz targets state the constitution's
   no-panic invariant and CI runs only their seed corpus, so the one check that finds this class of
   defect is the one nothing runs.
5. **The peak-memory bound has an unstated exclusion.** The synthetic log the bound is measured on
   holds three short ASCII names, so the claim is never tested against the one field shape that
   could break it.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - A live Gatling exercises the binary codec (Priority: P1)

A maintainer opens a pull request touching the binary decoder. Before it can merge, a real Gatling
of every version in the binary supported range runs the probe simulation, and the decoder is held to
the report each of those runs generated for itself — the same treatment the text codec already gets.

**Why this priority**: The recorded corpus proves the decoder against the past. Only a live run
proves it against a Gatling that exists now. The binary codec is the half with no such evidence, and
it is the half being frozen.

**Independent Test**: Point the verification at a freshly produced binary run directory and confirm
it decodes and matches that run's own account. Delivers the missing half of the canary on its own,
with nothing else in this feature built.

**Acceptance Scenarios**:

1. **Given** a Gatling in the binary supported range has just run the probe simulation, **When** the
   canary decodes that run, **Then** the decoded record stream matches the account that run gave of
   itself, and the check names the version it tested.
2. **Given** the supported range is widened without adding the new bound to the canary's version
   list, **When** the canary runs, **Then** it fails and names the version that was not exercised.
3. **Given** a Gatling above the supported range, **When** the canary decodes its run, **Then** the
   run decodes, a warning is surfaced, and the version is reported as a candidate for widening the
   range rather than failing the check.
4. **Given** fresh runs of two or more versions of the same probe, **When** they are compared with
   timing, run identity and record order set aside, **Then** they are identical as multisets, across
   the format boundary as well as within a format.

---

### User Story 2 - Per-request figures are checked against the run's own report (Priority: P2)

A maintainer changes how a request name, a group path or an outcome is decoded. The verification
compares not just the run's totals but every per-request row the tool's own report states, so a
change that moves a request between names, groups or outcomes fails even when the totals still add
up.

**Why this priority**: The constitution requires statistics to be compared against the report the
tool produced, and for the binary recordings that comparison currently reaches only three numbers.
Per-request agreement is what distinguishes a decoder that is correct from one that is merely
plausible in aggregate — which is exactly the claim the v0.1.0 freeze makes.

**Independent Test**: Run the verification over the existing recordings with no new corpus and no
live Gatling; every per-request figure the recorded reports carry is compared, and the count of
unchecked figures is reported as zero.

**Acceptance Scenarios**:

1. **Given** a recording whose report states per-request rows, **When** the verification runs,
   **Then** every request and every group named in that report is compared against the decoded
   records, and every row in the report is accounted for in the decoded stream and vice versa.
2. **Given** a recording from a version whose report states per-request rows only inside the
   rendered report rather than in a machine-readable file, **When** the verification runs, **Then**
   those rows are read from the report as the tool wrote it and compared the same way.
3. **Given** a recording is deliberately altered — one expected record's name changed — **When** the
   verification runs, **Then** the corresponding check fails and names the request that disagrees.
4. **Given** a version whose report genuinely carries no per-request figures, **When** the
   verification runs, **Then** the absence is stated by the recording and reported as an exclusion,
   never passed over in silence.
5. **Given** a future report shape the extraction does not recognise, **When** the verification
   runs, **Then** it fails saying no figures were found, rather than passing on an empty comparison.

---

### User Story 3 - The fuzzers run on every pull request (Priority: P3)

A maintainer opens a pull request that reintroduces a crash reachable only by a specific input. A
bounded fuzzing leg runs every fuzz target in the module, finds the crash, fails the pull request,
and attaches the input that caused it.

**Why this priority**: The constitution states that a decoder must not panic on any input. Nothing
enforces it. The defect this leg exists to catch — a cache index of the smallest 32-bit integer —
reached a pull request during v0.0.5 and was caught by a human reading the diff.

**Independent Test**: Reintroduce that defect on a branch and confirm the pull-request check fails
within its time budget, with the crashing input preserved.

**Acceptance Scenarios**:

1. **Given** a pull request, **When** verification runs, **Then** every fuzz target in the module is
   exercised beyond its seed corpus for a bounded time.
2. **Given** the v0.0.5 decoder with the smallest-32-bit-integer fix reverted, **When** the
   pull-request leg runs, **Then** it fails within its time budget.
3. **Given** the current decoder, **When** the pull-request leg runs, **Then** it passes within its
   time budget.
4. **Given** a fuzzer finds a crashing input, **When** the job ends, **Then** that input is
   preserved for download and the job is failed.
5. **Given** any fuzzing run, **When** the job ends, **Then** no generated fuzz corpus is committed
   to the repository.
6. **Given** the schedule rather than a pull request, **When** fuzzing runs, **Then** it runs for a
   longer budget than the pull-request leg.

---

### User Story 4 - One dispatch records a version (Priority: P4)

A new Gatling is released. A maintainer dispatches one job naming that version; it produces a
complete corpus entry — the log, the run's own account of itself in whatever shape that version
writes, and the decoded record stream to compare against — and publishes it for download. The
maintainer writes the recording note and commits.

**Why this priority**: The corpus is the specification for an undocumented format. A recording
procedure that is a page of prose and needs a local JDK, sbt and a stub is one that will be skipped,
and a version that is skipped is a version the gate cannot honestly be widened to.

**Independent Test**: Dispatch it for a version already in the corpus and confirm it reproduces that
entry's mechanical contents; dispatch it for a version not yet recorded and confirm it produces a
complete entry.

**Acceptance Scenarios**:

1. **Given** a supported Gatling version, **When** the recording job is dispatched with that
   version, **Then** it starts what the probe talks to, runs the probe under that version, and
   assembles the complete entry — including the run's own account, captured as the tool wrote it —
   with no manual file selection or copying and nothing installed locally.
2. **Given** the job has assembled an entry, **When** it finishes, **Then** the entry is published
   for download and is **not** committed to the repository by the job.
3. **Given** a version whose report shape differs from the previous one, **When** the job runs,
   **Then** it keeps what that version actually wrote and omits only what the report needs to
   render, without being told which shape to expect.
4. **Given** a version that cannot produce a report at all, **When** the job runs, **Then** it fails
   and says so, rather than publishing a partial entry that looks complete.
5. **Given** the probe run fails its own declared expectations, **When** the job runs, **Then** it
   fails, so a log that is merely self-consistent never enters the corpus.
6. **Given** a published entry, **When** its recording note is read, **Then** the note states the
   platform the run was made on, so an entry recorded on a runner is not mistaken for one recorded
   on a maintainer's machine.
7. **Given** an entry already in the corpus, **When** the job runs for that version, **Then**
   nothing it publishes can silently replace that entry's existing recording note.
8. **Given** the job has run, **When** the whole corpus is measured, **Then** it stays under a few
   megabytes.

---

### User Story 5 - The peak-memory bound covers a field at the ceiling (Priority: P5)

A maintainer changes how a string field is decoded in a way that doubles its transient cost. The
peak-memory check fails, because the log it measures against contains a field at the size ceiling in
every encoding the format can store one in.

**Why this priority**: The bound the reader documents is real and useful; today it is measured on a
log whose longest field is a handful of bytes. A bound with an unstated exclusion is not a bound —
and the excluded shape is the one the long-failure-message field exists for.

**Independent Test**: Add fields at the ceiling to the synthetic log and confirm the documented
budget either holds or is corrected together with the documentation, with no other part of this
feature built.

**Acceptance Scenarios**:

1. **Given** a synthetic log carrying one field at the string ceiling stored as single-byte ASCII,
   **When** it is decoded, **Then** the peak-memory assertion holds at the budget the reader's
   documentation states.
2. **Given** the same at the ceiling stored as single-byte text above ASCII, **When** it is decoded,
   **Then** the same assertion holds.
3. **Given** the same at the ceiling stored as two-byte text, **When** it is decoded, **Then** the
   same assertion holds.
4. **Given** the measured cost of a ceiling-sized field, **When** it exceeds the documented budget,
   **Then** exactly one of two things is done and recorded in the changelog — the ceiling is reduced
   until the documented budget holds, or the documented budget is restated to the measured figure —
   and lowering the exported ceiling is approved before it is made.
5. **Given** the reader's documented budget and the budget the check asserts, **When** either
   changes, **Then** they are the same number.

### Edge Cases

- **A Gatling version below the supported range** appears in a canary version list: the decode is
  refused with an error naming the version found and the range supported, and the canary reports the
  refusal as the expected outcome rather than a failure of the codec.
- **A Gatling version above the supported range**: the run decodes, the warning reaches the caller,
  and the canary reports it as a candidate for widening the range. It does not fail the build, and
  it is not compared for equality against in-range runs, because a warning is a statement about
  identity, not content.
- **A version that writes a log it cannot read back** (Gatling 3.13.0 today): the recording job
  fails. Nothing is published, because a run with no second, independent account of its numbers
  cannot prove anything.
- **A tool version stops producing a report**: the entry records that the absence is the tool's, and
  the verification reports the resulting exclusion by name.
- **A report shape the extraction does not recognise**: the check fails saying it found no figures.
  An empty comparison never passes.
- **A run with zero requests, or a truncated log**: the recording job fails rather than publishing
  an entry; the fuzz targets treat truncation as an error to be returned with a byte offset, never
  a panic.
- **A crashing input the fuzzer finds is itself large or unprintable**: it is preserved as a
  downloadable file, not pasted into the log.
- **A fuzzing leg finds nothing within its budget**: the leg passes. Absence of a finding within a
  bounded run is not evidence of correctness and is not reported as such.

## Requirements *(mandatory)*

### Functional Requirements

**Canary coverage (User Story 1)**

- **FR-001**: The canary MUST exercise a live Gatling of every version in both supported ranges,
  binary as well as text, and MUST hold each decoded run to the account that run gave of itself.
- **FR-002**: The canary MUST fail when a supported range's bound is not among the versions it ran,
  so the gate and the canary cannot drift apart.
- **FR-003**: The canary MUST compare fresh runs of the same probe against one another with timing,
  run identity and record order set aside, including across the text/binary format boundary, and
  MUST state which pairs it compared.
- **FR-004**: A canary version above the supported range MUST decode, MUST surface its warning in
  the run's summary, and MUST NOT fail the check or take part in the equality comparison.
- **FR-005**: The canary MUST fail when no canary check ran, so a skip can never be mistaken for a
  pass.

**Report-derived verification (User Story 2)**

- **FR-006**: For every recording, the verification MUST compare each per-request and per-group
  figure the run's own report states against the same figure folded from the decoded records.
- **FR-007**: The verification MUST read those figures from the artefacts as the tool wrote them,
  whatever shape that version wrote them in, and MUST NOT rely on figures extracted or summarised at
  recording time.
- **FR-008**: Every row the report names MUST be accounted for in the decoded stream, and every
  request and group in the decoded stream MUST be accounted for in the report; a mismatch in either
  direction MUST fail and name the row.
- **FR-009**: Counts MUST agree exactly; a figure that is a measurement rather than a count MUST be
  compared within a tolerance documented next to the assertion together with the reason for it.
- **FR-010**: A figure the report does not carry MUST be declared as an exclusion by name, and MUST
  be pinned against the recorded record stream instead.
- **FR-011**: The verification MUST fail when it extracts no figures from a report it was given.
- **FR-012**: A deliberately altered expected file MUST fail the corresponding check.

**Fuzzing in CI (User Story 3)**

- **FR-013**: Every fuzz target in the module MUST run beyond its seed corpus for a bounded time on
  every pull request.
- **FR-014**: The pull-request fuzzing budget MUST be large enough to reproduce the v0.0.5
  smallest-32-bit-integer crash on the CI runner, measured there rather than assumed.
- **FR-015**: A crashing input MUST be preserved as a downloadable artefact and MUST fail the job.
- **FR-016**: No generated fuzz corpus MUST be committed by any job.
- **FR-017**: A scheduled fuzzing run MUST use a longer budget than the pull-request leg.

**One-dispatch recording (User Story 4)**

- **FR-018**: Producing a corpus entry for a named version MUST be a single dispatch, run on a CI
  runner, that starts what the probe talks to, runs the probe under that version, selects the
  artefacts and produces the decoded record stream for comparison. It MUST require nothing installed
  on a maintainer's machine.
- **FR-019**: The job MUST publish the assembled entry for download and MUST NOT commit it. A corpus
  entry enters the repository through review, as any other change does.
- **FR-020**: The job MUST keep every artefact that carries a number, a name or a timestamp from the
  run exactly as the tool wrote it, and MUST omit only what the report needs to render.
- **FR-021**: The job MUST determine what that version writes from the run itself, not from a shape
  the caller declares.
- **FR-022**: The job MUST fail, publishing no entry, when the run produces no report or fails the
  expectations the probe declares.
- **FR-023**: The published entry MUST carry a recording-note scaffold stating the platform the run
  was made on, marked plainly as incomplete until the recorder finishes it; nothing the job produces
  MUST be able to replace an existing entry's note, which states what was checked at capture time
  and cannot be regenerated.
- **FR-024**: The whole corpus MUST stay under a few megabytes.

**Peak-memory bound (User Story 5)**

- **FR-025**: The peak-memory assertion MUST cover a field at the string ceiling in each encoding
  the format can store one in: single-byte ASCII, single-byte above ASCII, and two-byte.
- **FR-026**: The budget the peak-memory check asserts MUST be the budget the reader's documentation
  states.
- **FR-027**: The transient cost of decoding a field at the ceiling MUST be measured on the CI
  runner before either number is fixed. Neither the ceiling nor the documented budget is chosen in
  advance of that measurement.
- **FR-028**: If the measured cost exceeds the documented budget, exactly one of two outcomes MUST
  be taken and recorded in the changelog: the string ceiling is reduced until the documented budget
  holds, or the documented budget is restated to the measured figure. Reducing the exported ceiling
  changes the observable behaviour of a compatibility-sensitive API immediately before the v0.1.0
  freeze and MUST be approved before it is made.

### Key Entities

- **Corpus entry**: one recorded run of one tool version — the artefact as the tool wrote it, the
  account that tool gave of the run, the decoded record stream to compare against, and a note
  stating what was checked at capture time and what that version does not produce.
- **Run account**: whatever the tool states about its own numbers for one run. Its shape varies by
  version: a machine-readable summary, a rendered report, a console summary, or a combination. Some
  of it exists only if it was captured while the run happened.
- **Canary run**: a run produced by a live tool during the check, held to its own account and to the
  other canary runs of the same probe.
- **Fuzz target**: an invariant over arbitrary input — that no input reaches a panic — together with
  the seed corpus committed for it and the crashing inputs a run may produce.
- **Peak-memory budget**: the upper bound on heap while a log is decoded, stated once in the
  reader's documentation and asserted by one check.

### Source Coverage

- **Tool and versions**: Gatling 3.11.5 through 3.15.1 — the text range 3.11.5–3.12.0 and the binary
  range 3.13.1–3.15.1. Both ranges are exercised live; both are recorded.
- **Artefact formats**: text `simulation.log` (through 3.12.x) and binary `simulation.log` (3.13.1
  and newer). This feature adds no format and widens no gate.
- **Version gate**: unchanged. Below range is refused naming the version and the range; above range
  decodes with a warning surfaced to the caller. The canary reports an above-range run as a
  candidate for widening rather than as a failure.
- **Not provided by this source**: Gatling's report and console carry no count of virtual users and
  no count of error records; from 3.14.0 they carry no machine-readable per-request summary. Every
  such absence is declared by the recording and pinned against the recorded record stream instead.
- **Golden corpus**: the five entries already under `testdata/corpus/gatling/<version>/` —
  3.11.5, 3.12.0, 3.13.1, 3.14.9, 3.15.1 — one per version, each with that run's own report as
  captured at recording time. Gatling 3.13.0 is deliberately absent and the reason is recorded.
  This feature adds no version; it makes the existing entries reproducible by one dispatch and holds
  them to more of what their reports already say.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Every one of the five supported versions — text and binary — is exercised against a
  Gatling release that ran during the check, not only against a recording. Today three of the five
  are not.
- **SC-002**: The number of per-request and per-group figures a recording's report states that go
  uncompared is zero, or is named as an exclusion together with the reason the tool does not provide
  it.
- **SC-003**: Altering any single expected value in any recording fails exactly the check that
  covers it, and the failure names the value.
- **SC-004**: Recording a version takes one dispatch and the note the recorder writes; the number of
  manual file-selection or copying steps is zero, down from a nine-step written procedure, and the
  number of tools a maintainer must install locally is zero, down from three.
- **SC-005**: The whole recorded corpus stays under 5 MB.
- **SC-006**: Reintroducing the v0.0.5 smallest-32-bit-integer defect fails a pull request without a
  human reading the diff, and the input that proves it is downloadable from the failed run.
- **SC-007**: The peak-memory check holds for a field at the string ceiling in all three encodings,
  and the number the documentation states and the number the check asserts are the same — whichever
  of the two the measurement moved.
- **SC-008**: Every check added by this feature runs unattended in CI; none depends on a maintainer
  remembering to run it.

## Assumptions

- **The corpus stays at five versions.** No new Gatling version is recorded by this feature. The
  work is reproducibility and depth of verification over the entries that exist, which is what
  parsec#13 blocks on.
- **The probe simulation is unchanged.** Its shape — nested groups, both failure kinds, a
  Cyrillic request name, a repeated name that exercises the writer's string cache, a group name
  carrying a comma — already covers what the verification needs. Existing recordings that predate
  the current probe keep saying so in their own notes rather than being re-recorded.
- **Recording happens on a CI runner, not on a maintainer's machine.** One dispatch names the
  version; the runner runs the probe and publishes the finished entry for download. Removing the
  local JDK, sbt and stub from the procedure is what makes it repeatable when a new Gatling appears.
  Two consequences follow, and both are stated as requirements above: the job publishes rather than
  commits, so a corpus entry stays a reviewed act; and a new entry represents the runner's platform
  rather than a maintainer's, so its note must say which machine produced it. The five existing
  entries were recorded on macOS/arm64 and keep saying so — a corpus of mixed provenance is fine
  precisely because each entry states its own.
- **The recording note is written by the recorder, not generated.** It states what was checked at
  capture time and which absences are the tool's — judgements a job cannot make. The job scaffolds
  it, marked incomplete; it never replaces one.
- **The peak-memory numbers are settled by measurement during planning.** The specification fixes
  the invariant — the documented budget and the asserted budget are the same number, and it holds
  for a field at the ceiling — and deliberately fixes neither number. Whether the ceiling comes down
  or the budget goes up is decided from the measured figure, and lowering the exported ceiling needs
  approval before it is made.
- **Fuzzing runs on the pull request and on a schedule**, not on a schedule alone: the defect this
  exists to catch would otherwise have merged and been found the following morning.
- **A starting fuzz budget of about 90 seconds per target** is assumed for the pull-request leg,
  because that is roughly how long the reference defect took to find; the figure is confirmed by
  measurement on the CI runner and adjusted to whatever reproduces it there.
- **Statistics remain the consumer's arithmetic.** Every figure this feature compares is folded
  inside the verification suite. The module exports no count, mean, percentile, range or series, and
  this feature does not add one.
- **No third-party module is introduced.** The verification suite stays on the standard library,
  as `model/` and `gatling/` are required to.
- **The version gate is not widened.** Supported ranges are unchanged by this feature; the canary
  only proves the ranges already claimed.

## Dependencies

- **Blocks parsec#13** (the public API stability contract) — this milestone is the verification that
  makes the codecs safe to freeze at v0.1.0.
- Builds on the recordings and probe simulation delivered by specs 002, 003 and 005, and on the
  canary workflow that today covers the text versions.

## Out of Scope

- Performance benchmarks in CI.
- Fuzzing the text codec's line scanner beyond what its existing target does.
- Streaming decode of a single string; a field is decoded whole.
- Adding a Gatling version to the corpus or widening a supported range.
- Any adapter other than Gatling.
